# Открыватель шлагбаумов

Android-приложение для головных устройств в автомобиле. Автоматически распознаёт подъезд к настроенному шлагбауму по координатам и направлению движения и предлагает открыть его — звонком на привязанный номер, HTTP-запросом (webhook Home Assistant) или командой в Gate API — сервис, который ещё и показывает, в каком положении ворота.

## Про этот форк

Это форк проекта [DezzK/barrier-opener](https://github.com/DezzK/barrier-opener).

Оригинал открывает шлагбаум единственным способом — звонком на номер GSM-модуля.
Этого достаточно для типового дворового шлагбаума, но не покрывает случай, когда
воротами управляет умный дом: там открытие — это нажатие кнопки в Home Assistant,
а не телефонный звонок. Обходной путь через звонок требует, чтобы у ворот вообще
был GSM-модуль с номером, а у головного устройства — SIM-карта или спаренный по
Bluetooth телефон.

Поэтому форк добавляет второй способ открытия: HTTP-запрос по заданной ссылке.
Способ выбирается для каждого шлагбаума отдельно, так что обычные «звонковые»
шлагбаумы и ворота под управлением Home Assistant живут в одном списке. Вся
остальная механика оригинала — радиус, проверка направления подъезда, попап
поверх локскрина, кнопка «Подождать», список соседних шлагбаумов — работает
одинаково для обоих способов. Подробности настройки — в разделе
[Открытие через Home Assistant](#открытие-через-home-assistant) ниже.

Автор оригинала — Dezz ([@DezzK](https://t.me/DezzK)); ему же принадлежит
авторство почти всего кода. Форк остаётся под GPL-3.0, как того требует лицензия
оригинала.

## Возможности

- Список шлагбаумов с координатами, способом открытия и радиусом обнаружения.
- Срабатывание по **въезду** в зону: вопрос «Открыть?» ставится, только когда машина пересекла
  радиус снаружи внутрь (с гистерезисом против дрожания GPS), а не просто стоит внутри.
- Радиус закрытия отдельный от радиуса открытия: открывать можно издалека, чтобы медленные
  ворота успели, а закрывать — сразу за воротами.
- Три способа открытия на выбор для каждого шлагбаума: звонок на номер, POST-запрос по ссылке (с необязательным секретом в теле запроса) или Gate API с Bearer-токеном.
- Для Gate API — живой индикатор состояния ворот на карточке и в попапе, кнопки «Открыть» и «Закрыть», и никаких вопросов про уже открытые или уже закрытые ворота.
- Закрытие ворот с подтверждением — при отъезде, по таймеру и/или при переводе коробки в паркинг,
  тем же запросом либо отдельным.
- Предложение открыть ворота сразу после запуска — если машина стоит в зоне шлагбаума.
- Двунаправленные и односторонние шлагбаумы (с проверкой направления подъезда).
- Попап подтверждения поверх любого приложения и поверх локскрина (звук + full-screen notification).
- Кнопка-FAB «Сохранить» в нижней части экрана редактирования, карта Yandex MapKit на пол-экрана.
- Поиск точки по адресу прямо на карте (кнопка с лупой) с подсказками по мере ввода.
- Работает без Google Play Services (платформенный `LocationManager`, GPS + сетевой провайдер).
- Тёмная и светлая темы (Material 3, фирменная жёлтая палитра).
- Адаптивная иконка (foreground + monochrome для Android 13+).

## Как считается подъезд

Вопрос «Открыть шлагбаум X?» задаётся не потому, что машина находится внутри радиуса
обнаружения, а потому, что она **въехала** в него: предыдущие фиксы были снаружи, текущий
внутри. Машина, которая стоит в зоне с момента запуска сервиса (например, дома), въехавшей
не считается — для неё есть стартовый вопрос. Чтобы дрожание GPS на границе не превращалось
в бесконечные «въезды», выездом считается только уход за радиус плюс запас: не меньше 10 м
и не меньше четверти радиуса. Проверка курса по GPS (в пределах 45° на ворота, а для
односторонних — ещё и направление проезда) остаётся как второй, независимый фильтр.

## Gate API

Ворота под управлением умного дома лучше всего подключать через Gate API — небольшой
сервис рядом с Home Assistant, который знает положение ворот (по двум герконам) и
принимает явные команды. В отличие от webhook'а здесь «открыть» и «закрыть» — разные
команды, а не один импульс, поэтому повторный «закрыть» на уже закрытых воротах ничего
не делает, и приложение может показать, что с воротами происходит.

### Настройка в приложении

В форме шлагбаума выберите способ открытия «Gate API» и заполните два поля:

- **Адрес Gate API** — схема и хост, например `https://gate-api.example.com`. Пути
  (`/v1/gate`, `/v1/gate/open`…) приложение добавляет само.
- **Токен доступа** — выдаёт владелец ворот, один на машину. Уходит заголовком
  `Authorization: Bearer <токен>`; в теле и в URL секретов нет. В поле ввода токен скрыт.

Кнопка «Проверить» делает `GET /v1/gate` с введённым токеном и показывает состояние ворот
или ошибку — неверный токен виден сразу как «Неверный токен», а не при первом нажатии у
ворот. У второго и следующих шлагбаумов на том же сервисе адрес и токен подставляются из
последнего сохранённого. Хранятся они так же, как секрет webhook'а — в строке шлагбаума.

### Что шлёт приложение

| Когда | Запрос |
|---|---|
| Подъезд к воротам, стартовый вопрос, кнопка «Открыть» | `POST /v1/gate/open` |
| Триггеры закрытия (отъезд, таймер, паркинг), кнопка «Закрыть» | `POST /v1/gate/close` |
| Индикатор состояния | `GET /v1/gate` раз в 2 с |
| Перед вопросом «Открыть?» / «Закрыть?» | `GET /v1/gate` один раз |
| Проверка доступности перед вопросом | `GET /healthz` (без токена), при сетевой ошибке — TCP-коннект к хосту |

Команды уходят пустым POST без ожидания результата (`?wait=1` не используется: долгое
соединение через KeenDNS ненадёжно), ответ `202` считается успехом (тост «Команда принята»),
а объект состояния из него сразу попадает в индикатор — в нём ворота ещё в прежнем положении,
`moving` станет `true` через 1–2 с. Команды `stop` и `open-slightly` у сервиса есть, но
приложению они не нужны: оно открывает ворота, к которым подъезжает, и закрывает те, от
которых уехало. Таймауты: 7 с на соединение, 10 с на
ответ. Автоповторов нет: ретраи делает Home Assistant, а повтор при `429` бесполезен.
Идентификатор запроса (`request_id`) пишется в logcat — он совпадает с аудит-логом сервиса.

### Индикатор состояния

На карточке шлагбаума в списке и в попапе показывается состояние ворот: «Закрыты»,
«Открыты», «Открываются…», «Закрываются…», «Приоткрыты», «Неизвестно». Опрос идёт раз в
2 с и только пока экран виден — в фоне приложение сервис не опрашивает. Отставание
индикатора от физики в 3–5 с нормально.

Состояние показывается приглушённо с пометкой «данные устарели», если сервис сообщил, что
сам не достучался до Home Assistant (`ha: unreachable` или `age_seconds` больше 10), либо
если последний успешный `GET` с магнитолы был больше 10 с назад. Часы магнитолы при этом
не участвуют: они плывут, и сравнение с серверным `updated` давало бы ложные «устарели».

Кнопки, которые сервер в текущем состоянии не считает осмысленными (поле `allowed`),
приглушаются, но не блокируются: при «Неизвестно» список пуст, а нажать всё равно может
понадобиться. После нажатия кнопки замирают на 2 с — столько сервис держит паузу между
любыми командами.

### Ошибки

Как и везде в приложении, ошибка — это тост, другого канала у водителя за рулём нет:

| Ответ | Тост |
|---|---|
| `401 unauthorized` | «Неверный токен» |
| `429 cooldown` / `429 rate_limited` | «Слишком рано, подожди N с» (N из `Retry-After`) |
| `503 ha_unavailable` | «Home Assistant недоступен» — команда не отправлена |
| нет ответа, таймаут | «Нет связи с сервером ворот» |

### Вопросы об открытии и закрытии

Перед любым вопросом приложение один раз спрашивает сервис, где ворота:

- **«Открыть ворота?»** (подъезд или стартовый вопрос) не задаётся, если ворота уже открыты
  или открываются — вместо него тост «Ворота уже открыты», и шлагбаум считается
  сработавшим, как после показанного попапа. Если ворота прочитать не удалось (нет сети,
  HA недоступен), вопрос задаётся как раньше: на подъезде важнее появиться до ворот.
- **«Закрыть ворота?»** не задаётся, если ворота уже закрыты — тост «Ворота уже закрыты», и
  запись о незакрытых воротах снимается. Если сервис отвечает, что Home Assistant
  недоступен, вопрос не задаётся и не «тратится» — он повторится через 15 с, как и при
  молчании хоста.

## Открытие через Home Assistant (webhook)

> **Устаревшее.** Схема с webhook'ами остаётся для совместимости, пока оба клиента (машина и
> Telegram-бот) не переедут на Gate API, после чего будет удалена. Новые ворота подключайте
> через [Gate API](#gate-api).

Для шлагбаума выберите способ открытия «HTTP-запрос» и укажите ссылку на webhook.
Поле «Секрет» необязательное: если оно пустое, приложение шлёт пустой `POST` — ровно
то же, что делает `curl -X POST <url>`. Если секрет задан, он уходит JSON-телом:

```json
{"secret": "<ваш-секрет>"}
```

Автоматизация на стороне HA — с проверкой обоих факторов:

```yaml
triggers:
  - trigger: webhook
    webhook_id: !secret gate_webhook_id
    allowed_methods: [POST]
    local_only: false
variables:
  expected_secret: !secret gate_webhook_secret
conditions:
  - condition: template
    value_template: >-
      {{ trigger.json is defined and trigger.json.secret is defined
         and trigger.json.secret == expected_secret }}
  - condition: template
    value_template: >-
      {{ this.attributes.last_triggered is none
         or (now() - this.attributes.last_triggered).total_seconds() > 5 }}
actions:
  - action: input_button.press
    target:
      entity_id: input_button.gates
```

Ссылка для приложения — `https://<ваш-ha>/api/webhook/<webhook_id>`. Проверить:

```bash
curl -X POST -H 'Content-Type: application/json' \
     -d '{"secret":"<ваш-секрет>"}' \
     https://<ваш-ha>/api/webhook/<webhook_id>
```

### Открытие при запуске

Отдельный случай — момент, когда вы только сели в машину и завели её. Обычное
обнаружение здесь молчит: машина стоит, направление подъезда определить не по чему,
а шлагбаум почти наверняка ещё помечен как сработавший со вчерашнего заезда.

А на головах, которые отдают передачу, оно молчит гарантированно: пока коробка в P,
обычный триггер подъезда не срабатывает вообще. Стоящая машина ни к каким воротам не
подъезжает, а верить фиксу тут нельзя: GPS на голове поднимается заметно позже
двигателя, и его первые фиксы несут направление, собранное из шума. Для
двунаправленного шлагбаума, внутри радиуса которого машина и стоит, направление
вообще не требуется — и этого хватало, чтобы предложить открыть ворота ещё до того,
как водитель пристегнулся. Там, где передачу прочитать нельзя, всё работает
по-прежнему.

Поэтому при старте сервиса (а на голове это загрузка, то есть зажигание) приложение
один раз спрашивает: «Открыть шлагбаум X?» — если машина стоит внутри радиуса
обнаружения. Вопрос ждёт, пока поднимутся GPS и сеть: у HTTP-шлагбаума запрос без сети
всё равно не уйдёт, а Wi-Fi на голове поднимается на десяток секунд позже первого
фикса. Если за пять минут после старта условия так и не сложились, предложение
снимается — попап через полчаса после запуска был бы уже неожиданностью, а не помощью.

На головах Geely/ECARX, которые отдают состояние машины, в форме шлагбаума, в блоке
«При запуске машины», можно включить ещё два ожидания. По умолчанию оба выключены:

- **Ждать, пока водитель пристегнётся.** При удалённом запуске двигатель работает,
  а в машине никого нет — попап показался бы в пустом салоне, закрылся по таймауту,
  и вопрос был бы потрачен. Поэтому, пока ремень водителя не пристёгнут, вопрос
  не задаётся.
- **Ждать прогрева двигателя.** Пока коробка в P, а обороты 1000 и выше, машина
  греется, и ворота открывать рано. Как только обороты опустились ниже 1000 — попап
  появляется.

Пока машина ждёт водителя или прогрева, пятиминутное окно не тикает, так что ни
удалённый запуск, ни долгий зимний прогрев вопрос не съедают. Перевод коробки из P
(в D или R) снимает оба ожидания сразу: вы уже поехали. Если ремень или обороты
прочитать нельзя, это условие просто не проверяется. На голове, которая вообще не
сообщает состояние машины, под переключателями написано, что они ни на что не влияют.

Спрашивается всегда только ближайший шлагбаум — тот, у которого машина и стоит.
Отдельного переключателя у этой функции нет: приложение ничего не открывает само,
а просто задаёт вопрос, на который можно ответить «Нет».

### Закрытие ворот

Для HTTP- и Gate-API-шлагбаумов в форме есть блок «Закрытие» с тремя независимыми триггерами —
включать можно любые вместе, срабатывает тот, что раньше:

- **При отъезде** — когда машина **побывала у ворот**, то есть ближе радиуса закрытия, и
  затем вышла за него плюс небольшой запас (5 м). Радиус закрытия — своя настройка в этом
  блоке, по умолчанию равна радиусу обнаружения, но смысл в том, чтобы сделать её маленькой:
  радиус обнаружения ставят большим, чтобы медленные ворота успели открыться, пока машина
  едет, а закрывать хочется сразу за воротами. Условие «побывала у ворот» и делает маленький
  радиус безопасным: вопрос об открытии задаётся далеко, и без него машина считалась бы
  «уехавшей» в момент ответа «Да». Запас — это гистерезис, а не расстояние: он нужен ровно
  для того, чтобы дрожание GPS на границе не дёргало попап, пока машина ещё стоит у ворот.
  На карте в форме редактирования порог закрытия показан отдельным оранжевым кругом.
  Радиус закрытия не стоит ставить меньше 5–10 м: нужен хотя бы один фикс GPS внутри него,
  пока машина проезжает ворота.
- **По таймеру** — через заданное число минут после открытия, **если машина всё ещё в зоне**.
  Это страховка на случай, когда машина осталась внутри или GPS не зафиксировал отъезд;
  уехали — вопросом займётся триггер отъезда.
- **При переводе в паркинг** — когда селектор коробки ушёл в P **внутри зоны**: поездка
  закончена, машина дома и стоит. Паркинг в другом районе про эти ворота ничего не говорит. Это самый точный из трёх сигналов, но работает только на головных
  устройствах, которые отдают приложениям положение коробки через `android.car`
  (Android Automotive и построенные на нём штатные головы). Срабатывание считается по
  *переходу* в P: машина и так стоит в паркинге в момент запуска, и вопрос при заводке
  был бы не к месту.

  Доступ к коробке закрыт разрешением `android.car.permission.CAR_POWERTRAIN`. Оно
  «опасное»: объявить его в манифесте мало, система спрашивает его отдельно — приложение
  запросит доступ в тот момент, когда вы включите этот переключатель.

  Передача читается из трёх источников по очереди: вендорского ECarX AdaptAPI
  (`ISensor.SENSOR_TYPE_GEAR` — именно он работает на Монжаро), штатного `CarPropertyManager`
  и legacy-`CarSensorManager`. Источник считается рабочим, только если он отдаёт осмысленное
  значение: на Монжаро, например, `CarPropertyManager` публикует пустой список свойств и
  отвечает «передача неизвестна» на любой запрос.

  Оба триггера — таймер и паркинг — молчат, если фикса нет вообще: вопрос про ворота,
  до которых может быть несколько километров, хуже открытых ворот.

  Перед тем как задать вопрос — и про открытие при запуске, и про закрытие — приложение
  проверяет, что хост ворот вообще отвечает (TCP-соединение с адресом из ссылки, без
  самого запроса: «проверить» вызовом webhook означало бы открыть ворота). Голова
  подключается к домашнему Wi-Fi через несколько секунд после запуска двигателя, и до
  этого момента нажатое «Да» уходило в никуда с одним лишь тостом об ошибке. Пока хост
  не ответил, вопрос не задаётся, а «спросили один раз» не тратится — как только сеть
  поднимется, вопрос придёт.

  Если голова вообще не отдаёт приложениям данные машины, под переключателем написано,
  что этот триггер на ней не сработает.

В обоих случаях приложение **спрашивает подтверждение** — само по себе ничего не
закрывается. Вопрос задаётся один раз: если вы ответили «Нет» или попап закрылся сам,
повторно приложение не переспрашивает.

Ссылка и секрет для закрытия необязательные. Пустая ссылка означает «закрывать тем же
запросом, что открывает» — это случай toggle-ворот, где один и тот же webhook переключает
состояние. Если контроллер разделяет команды, укажите отдельный URL и, при необходимости,
отдельный секрет:

```yaml
triggers:
  - trigger: webhook
    webhook_id: !secret gate_close_webhook_id
    allowed_methods: [POST]
    local_only: false
variables:
  expected_secret: !secret gate_close_secret
conditions:
  - condition: template
    value_template: >-
      {{ trigger.json is defined and trigger.json.secret is defined
         and trigger.json.secret == expected_secret }}
actions:
  - action: input_button.press
    target:
      entity_id: input_button.gates_close
```

Закрытие доступно только для HTTP-шлагбаумов. У звонковых оно не предлагается: повторный
звонок на GSM-модуль переключает состояние непредсказуемо, а такие шлагбаумы обычно
закрываются сами по таймеру контроллера.

### Почему секрет в теле, а не в заголовке

Webhook-триггер HA отдаёт шаблонам только `trigger.json` (JSON-тело), `trigger.data`
(form-encoded) и `trigger.query` (query-параметры). HTTP-заголовки шаблонам недоступны,
поэтому проверить секрет из заголовка вроде `X-Gate-Secret` автоматизация не сможет.
Query-параметр отпадает по другой причине: он уходит в URL, а URL оседает в логах
прокси и в истории — второго фактора это не создаёт. Остаётся тело запроса.

Сам `webhook_id` — тоже секрет, он передаётся в URL: берите длинную случайную строку
и предпочитайте `https`. Адреса `http://` в локальной сети тоже работают (в манифесте
разрешён cleartext-трафик), но учтите, что по такому адресу и секрет из тела идёт
открытым текстом. `local_only: false` нужен, только если ГУ ходит в HA снаружи домашней сети.

Второе условие в автоматизации — дебаунс в 5 секунд: у откатных ворот повторный
импульс означает «стоп», поэтому команда, пришедшая раньше чем через 5 с, сознательно
игнорируется. По той же причине приложение не делает автоповторов при ошибке — если
запрос не прошёл, решение о повторе остаётся за водителем.

Всё остальное работает одинаково для обоих способов открытия: радиус, проверка
направления, кнопка «Подождать» и список соседних шлагбаумов в попапе.

## Требования

- Android 9 (API 28) и новее.
- GPS на устройстве. Network-провайдер используется как страховка.
- Yandex MapKit API key — получите бесплатно в [Yandex Cloud](https://developer.tech.yandex.ru/).
  Поиск по адресу работает по тому же ключу: подсказки и геокодирование входят в MapKit,
  отдельный сервис подключать не нужно. Бесплатной лицензии (1000 уникальных пользователей
  в сутки) для личного использования хватает с запасом.

## Локальная сборка

API-ключ MapKit можно положить в `local.properties` (он в `.gitignore`):

```properties
YANDEX_MAPKIT_API_KEY=ваш-ключ
```

либо передавать через переменную окружения. Для отладочной сборки:

```bash
./gradlew assembleDebug
```

Для подписанного релиза нужен `keystore.jks` в корне репозитория и переменная `KEY_PASSWORD`:

```bash
VERSION_NAME=v0.3.0 \
KEY_PASSWORD=пароль \
YANDEX_MAPKIT_API_KEY=ключ \
./gradlew assembleRelease
```

`VERSION_NAME` парсится в `versionCode` (`v0.3.1` → `301`). Готовый APK: `app/build/outputs/apk/release/barrier-opener-${VERSION_NAME}-release.apk`.

Установка на ГУ через ADB:

```bash
adb install -r app/build/outputs/apk/release/barrier-opener-v0.3.0-release.apk
```

Страница оригинального проекта: <https://dezzk.github.io/barrier-opener/>.
